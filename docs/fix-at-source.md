# Fix at the source: the pull request that ends the incident

Restoring the rule at 03:15 is a patch on the account. The cause was a change, and the durable fix lives in the infrastructure code. Beacon's night ends with a pull request, opened by voice, never merged by Beacon.

```
resolved (verified) ──► Beacon: "The runtime fix is in. The durable fix is a pull request — say 'open the pull request'."
engineer: "open the pull request"
   ──► open_fix_pr(confirmation_phrase)          consent: phrase in the transcript, an approval on record
       ──► GitHub: branch beacon/incident-<id>
           ├─ demo/demo-infra-template.yaml       + AWS::EC2::SecurityGroupIngress   (only when the template lacks the rule)
           └─ docs/incidents/<date>-<alarm>-<id>.md  the postmortem the API already generates
       ──► PR "Restore RdsSecurityGroup ingress from EcsSecurityGroup (Beacon incident …)"
           body: the approval quote (channel, time, STT confidence, session), the verify checks,
                 the CloudTrail change behind it, the console link
   ──► timeline event pr_opened {url}; the console card and the morning report link to it
```

## What is decided by code and what by the model

| Decision | Made by |
|---|---|
| Whether to call `open_fix_pr` | the model — only after the engineer says *open the pull request* (or *pull request kholo*) |
| Whether the call is allowed | code: the phrase must be in the transcript; an approval record must exist for the incident (a fix was applied); the repo and token must be configured |
| What the patch is | code: for `sg.restore_ingress`, the security groups are mapped to the template's logical ids through the `aws:cloudformation:logical-id` tags CloudFormation sets; the template is parsed; if it does not declare the rule (inline on the group or as a standalone resource), an `AWS::EC2::SecurityGroupIngress` with the dry-run's exact parameters is appended before `Outputs:`. If it does declare it, the revoke was out-of-band and the PR says so, naming the CloudTrail actor. For `ecs.force_redeploy` there is no code change. |
| The PR text | code, from the incident record — no prose is generated by a model |

The patch uses the same `params` that passed the dry run and were executed under the remediator role, so what lands in review is exactly what fixed production.

## Set-up

1. Fork or choose the infrastructure repository (for the demo, a fork of this one). Create a **fine-grained personal access token** limited to that repository with *Contents: read and write* and *Pull requests: read and write*.
2. ```
   make set-fix-pr-token GITHUB_PR_TOKEN=github_pat_… FIX_PR_REPO=<owner>/<repo>
   make deploy-console …          # same flags as before
   ```
   `set-fix-pr-token` stores the token in SSM (`/beacon/<stack>/github-pr-token`) and saves `FIX_PR_REPO` in `.beacon.env`; `deploy-console` passes them to the voice Lambda (`FIX_PR_TOKEN_PARAM`, `FIX_PR_REPO`, optional `FIX_PR_BASE`, `FIX_PR_TEMPLATE_PATH`).
3. To show a real code change in the demo, remove the `SecurityGroupIngress` block from `demo/demo-infra-template.yaml` on the fork's `main` (the story: a deploy dropped the rule). With the block present, the PR carries the postmortem and the out-of-band finding.

## Security

- The token never leaves SSM except into the voice Lambda's memory; it is scoped to one repository and cannot merge (branch protection is yours to set).
- `open_fix_pr` is a consent tool: the phrase is checked against the transcript like `approve fix 1`, and the call is refused without an approval record — a PR is never opened for a fix that was not applied.
- The branch name is derived from the incident id; re-running the tool reuses the branch and updates the files rather than opening duplicates.
